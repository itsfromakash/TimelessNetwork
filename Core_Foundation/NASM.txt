IMPORTANT:

ABI is NOT simply:

    C -> Compiler -> Assembly -> ABI -> Object

Instead ABI is a CONTRACT used across the whole binary interface.

ABI defines things such as:

    - argument passing
    - return values
    - register preservation
    - stack layout
    - stack alignment
    - structure passing
    - structure return
    - symbol naming
    - object/binary conventions
    - calling convention

01. CPU BASICS
===============================================================================

CPU mainly works with:

    Registers
    Memory
    Instructions
    Flags

Example:

    mov eax, 10
    add eax, 20

Conceptually:

    EAX = 10
    EAX = EAX + 20

Final:

    EAX = 30

===============================================================================

    1 bit   = 0 or 1
    8 bits  = 1 byte
    16 bits = 2 bytes
    32 bits = 4 bytes
    64 bits = 8 bytes

Common sizes:

    BYTE    = 8
    WORD    = 16
    DWORD   = 32
    QWORD   = 64

    OWORD   = 128
    YWORD   = 256

03. GENERAL PURPOSE REGISTERS
===============================================================================

Register family       64-bit     32-bit     16-bit     8-bit

Accumulator           RAX        EAX        AX         AL
Base                  RBX        EBX        BX         BL
Counter               RCX        ECX        CX         CL
Data                  RDX        EDX        DX         DL

Source Index          RSI        ESI        SI         SIL
Destination Index     RDI        EDI        DI         DIL

Register 8            R8         R8D        R8W        R8B
Register 9            R9         R9D        R9W        R9B
Register 10           R10        R10D       R10W       R10B
Register 11           R11        R11D       R11W       R11B
Register 12           R12        R12D       R12W       R12B
Register 13           R13        R13D       R13W       R13B
Register 14           R14        R14D       R14W       R14B
Register 15           R15        R15D       R15W       R15B


IMPORTANT:

    RAX
     |
     +-- EAX
           |
           +-- AX
                |
                +-- AL

These are NOT four independent registers.

They are different-width views of the same register family.

===============================================================================

    AH
    BH

    AX = AH:AL

    +----------------+--------+
    |       AH       |   AL   |
    |     8 bits     | 8 bits |

For modern x86-64 code, low-byte registers such as:

are generally easier to use.


===============================================================================
05. 32-BIT WRITE ZERO-EXTENSION
===============================================================================

VERY IMPORTANT x86-64 RULE:

Writing a 32-bit GPR generally zeroes the upper 32 bits.

Example:

    mov rax, 0xFFFFFFFFFFFFFFFF
    mov eax, 10

After:

    RAX = 0x000000000000000A


But writing 16-bit does NOT zero upper bits:

    mov rax, 0xFFFFFFFFFFFFFFFF
    mov ax, 10

Result:

    RAX = 0xFFFFFFFFFFFF000A


Writing 8-bit does NOT zero upper bits either.

===============================================================================
18. POINTERS
===============================================================================

A pointer is an address.

On x86-64:

    pointer = typically 64-bit


Example C:

    int *p;


Conceptually:

    p = address


NASM:

    mov rax, [p]       ; load data from memory
    lea rax, [p]       ; calculate/load address


IMPORTANT:

    mov rax, [p]

means:

    load VALUE at address p


    lea rax, [p]

means:

    calculate ADDRESS expression


===============================================================================
19. MOV
===============================================================================

MOV copies data.

    mov destination, source


Examples:

    mov eax, ebx

    mov rax, 123

    mov al, 10

    mov rax, [rbx]

    mov [rbx], rax


MOV does not mean mathematical movement.

It means:

    destination = source


===============================================================================
20. LEA
===============================================================================

LEA = Load Effective Address

Example:

    lea rax, [rbx + rcx*4 + 8]


This calculates:

    RAX = RBX + RCX*4 + 8


It does NOT load memory from that address.

===============================================================================
35. STACK
===============================================================================

Stack grows toward LOWER addresses on x86-64.


RSP = current stack pointer


PUSH:

    push rax


conceptually:

    RSP = RSP - 8
    [RSP] = RAX


POP:

    pop rax


conceptually:

    RAX = [RSP]
    RSP = RSP + 8


For 64-bit push/pop.


===============================================================================
36. STACK FRAME
===============================================================================

Traditional function:

    push rbp
    mov rbp, rsp

    ...

    mov rsp, rbp
    pop rbp
    ret


Stack frame:

        higher addresses
              |
              v

    +-----------------------+
    | caller data           |
    +-----------------------+
    | return address        |
    +-----------------------+
    | saved RBP             |
    +-----------------------+
    | local variables       |
    +-----------------------+
              ^
              |
             RSP


RBP is optional in optimized code.

Do NOT assume:

43. ABI REGISTER WIDTH
===============================================================================

If ABI selects:

    RCX

then possible views are:

    64-bit -> RCX
    32-bit -> ECX
    16-bit -> CX
    8-bit  -> CL


If ABI selects:

    RDI

then:

    64-bit -> RDI
    32-bit -> EDI
    16-bit -> DI
    8-bit  -> DIL


IMPORTANT:

    "a -> RCX"

is shorthand.

Precise:

    "value of the first parameter a is passed
     through the RCX register family under Windows x64."

47. CALLER-SAVED vs CALLEE-SAVED
===============================================================================

    caller must preserve values if it needs them
    across a function call.


CALLEE-SAVED:

    callee must restore original values before returning

Another naming:

    caller-saved = volatile
    callee-saved = nonvolatile

60. SYSTEM CALLS
===============================================================================

A user program needs OS services:

    files
    processes
    memory
    sockets
    etc.


It enters the kernel through an OS-defined system-call interface.


IMPORTANT:

    Windows system calls
    !=
    Linux system calls
    !=
    macOS system calls


The ABI/API boundary is OS-specific.


Linux x86-64 syscall convention uses registers such as:

    RAX = syscall number
    RDI = arg1
    RSI = arg2
    RDX = arg3
    R10 = arg4
    R8  = arg5
    R9  = arg6


Then:

    syscall


IMPORTANT:

    Linux syscall ABI is NOT identical to the normal
    SysV C function calling convention.

Notice:

    normal 4th argument -> RCX

but syscall 4th argument -> R10

    system frameworks
    system APIs

rather than writing raw kernel syscall code as the normal application model.


x86-64 macOS ABI:

    System-V-derived


Apple Silicon:

    ARM64

different architecture.


===============================================================================
63. SYSTEM CALL != FUNCTION CALL
===============================================================================

Function call:

    call function


System call:

    user -> kernel transition


Function call stays within normal process execution context.

System call crosses privilege boundary into OS kernel.


===============================================================================
64. PROCESS MEMORY LAYOUT
===============================================================================

Typical conceptual process:

    HIGH ADDRESSES
    +-------------------------+
    | Stack                   |
    |                         |
    |          ↓              |
    +-------------------------+
    |                         |
    | mmap / shared libraries |
    |                         |
    +-------------------------+
    |          ↑              |

    | .bss                    |
    +-------------------------+

    +-------------------------+
    | .rodata                 |
    +-------------------------+
    | .text                   |
    +-------------------------+
    LOW ADDRESSES


Actual layout varies by OS, loader, ASLR, architecture and executable.

    stack
    heap

to make exploitation harder.

67. NX / DEP

    Write
    Execute

69. STRUCT LAYOUT
===============================================================================

C:

    struct Point
    {
        int x;

===============================================================================
72. POINTER ARITHMETIC
===============================================================================

    p + 1


does NOT necessarily mean:

    address + 1 byte


It means:

    address + sizeof(*p)


Example:

    int *p

then:

    p + 1

means:

    address + 4


Assembly must explicitly calculate the correct byte offset.

===============================================================================
76. NASM DIRECTIVES vs INSTRUCTIONS
===============================================================================

INSTRUCTION:

    mov
    add
    sub
    call
    ret


DIRECTIVE:

    assembler processes it.

Examples:

    global
    extern
    section
    db
    dq

The assembler uses it when generating object code.


===============================================================================
77. REGISTER vs MEMORY
===============================================================================

Register:

    mov eax, ebx


Memory:

    mov eax, [rbx]


Difference:

    mov eax, ebx

means:

    EAX = EBX


    mov eax, [rbx]

means:

    EAX = memory at address RBX


The brackets matter.


===============================================================================
78. ADDRESS vs VALUE
===============================================================================

Suppose:

    RAX = 0x1000


and:

    [0x1000] = 123


Then:

    mov rbx, rax

gives:

    RBX = 0x1000


But:

    mov rbx, [rax]

gives:

    RBX = 123


Very important:

    RAX       = address
    [RAX]     = data at that address


===============================================================================
79. STACK ARGUMENTS
===============================================================================

If registers are insufficient:

    arguments go to memory/stack according to ABI.


Windows:

    first four integer argument slots use:

        RCX RDX R8 R9

    additional arguments use stack.


SysV:

    first six integer/pointer arguments:

        RDI RSI RDX RCX R8 R9

    additional arguments use stack.


Complex aggregates can alter this simple picture.


===============================================================================
80. MIXED INTEGER + FP ARGUMENTS
===============================================================================

Do NOT use a simplistic:

    "count integers separately"
    "count floats separately"

model for every ABI case.


Real ABIs classify arguments by:

    type
    size
    position
    aggregate classification
    register availability


Especially important for:

    struct
    union
    vector
    mixed integer/FP
    variadic functions


The Microsoft x64 ABI also has important positional rules for FP arguments.


===============================================================================
81. VARIADIC FUNCTIONS
===============================================================================

Example:

    printf("%d %f", x, y);


Variadic calls have additional ABI requirements.


Windows x64:

    floating-point values passed to variadic/unprototyped functions
    have special register/home-space behavior.


SysV AMD64:

    uses additional state such as:

        AL

to communicate the number of vector registers used for
certain variadic calls.


Therefore:

    printf

is an important ABI case study.


===============================================================================
82. C CALLING CONVENTION
===============================================================================

C compiler generates caller and callee according to ABI.


Caller responsibilities can include:

    argument setup
    stack setup
    preserving caller-saved values
    call


Callee responsibilities can include:

    preserving callee-saved registers
    local stack allocation
    returning correct result
    restoring stack state


===============================================================================
83. FUNCTION PROLOGUE
===============================================================================

Possible:

    push rbp
    mov rbp, rsp
    sub rsp, 32


Meaning:

    save old frame pointer
    establish frame
    reserve locals


But exact prologue depends on:

    compiler
    optimization
    ABI
    local variables
    register usage
    stack alignment


===============================================================================
84. FUNCTION EPILOGUE
===============================================================================

Possible:

    add rsp, 32
    pop rbp
    ret


Or:

    mov rsp, rbp
    pop rbp
    ret


Optimized functions may have no RBP frame.


===============================================================================
85. REGISTER SAVE EXAMPLE
===============================================================================

Suppose a function wants to modify RBX on SysV.


RBX is callee-saved.

Therefore:

    push rbx

    ...
    ; modify RBX

    pop rbx
    ret

    original RBX

    RCX/RDI = address

107. COMMON NASM ERRORS
===============================================================================

    mov eax, rbx

    EAX = 32-bit
    RBX = 64-bit

Widths don't match.

    mov rax, rbx


or:

    mov eax, ebx

===============================================================================
108. MEMORY-TO-MEMORY MOV
===============================================================================

Generally x86 MOV does NOT allow:

    mov [a], [b]


Use a register:

    mov rax, [b]

There are special string instructions for memory-to-memory
operations, but normal MOV is register/immediate/memory with
the normal x86 operand restrictions.

134. FLAGS + ARITHMETIC
===============================================================================

===============================================================================
135. CARRY vs OVERFLOW
===============================================================================

Carry:

    mainly relevant to unsigned arithmetic.


Overflow:

    signed integer overflow.


Example 8-bit signed:

    127 + 1


bits:

    01111111
    +
    00000001
    ----------
    10000000


Interpreted signed:

    -128


Therefore:

    OF = 1


===============================================================================
136. ZEROING REGISTERS
===============================================================================

Common:

    xor eax, eax


or:

    mov eax, 0

    xor eax, eax

for architectural/encoding reasons.


===============================================================================
137. XOR ZEROING AND FLAGS
===============================================================================

    xor eax, eax


sets:

    EAX = 0


and also modifies flags.


Therefore if flags matter, don't blindly replace instructions
without understanding the flag effects.

===============================================================================
142. DEPENDENCIES
===============================================================================

Example:

    add rax, rbx
    add rax, rcx


Second instruction depends on first result.


Dependency chain can limit throughput.


Independent:

    add rax, rbx
    add rdx, rcx


can potentially execute more independently.


Actual performance depends on CPU microarchitecture.


===============================================================================
143. BRANCH PREDICTION
===============================================================================

Conditional:

    cmp
    jne


CPU predicts branch direction.


Wrong prediction:

    pipeline work may be discarded.


Performance-sensitive code often cares about:

    predictable branches
    branchless operations
    data locality


But "branchless is always faster" is FALSE.


===============================================================================
144. ATOMICITY
===============================================================================

Single instruction does not automatically mean:

    universally atomic


Atomicity depends on:

    instruction
    alignment
    memory type
    architecture
    operand size
    concurrency model


Use proper atomic primitives and language/OS facilities.


===============================================================================
145. MEMORY ORDERING
===============================================================================

Concurrent systems require understanding:

    compiler ordering
    CPU ordering
    cache coherence
    fences
    acquire/release
    sequential consistency


Instructions:

    LFENCE
    SFENCE
    MFENCE


and atomic instructions can participate.


===============================================================================
146. RED ZONE
===============================================================================

IMPORTANT Linux/macOS SysV concept:

    128-byte red zone

exists below RSP for normal SysV AMD64 user-space code.


Signal/interrupt handling rules matter.


Windows x64 does NOT use the SysV red zone.


Therefore:

    SysV assembly may use red-zone assumptions
    Windows assembly must not assume a SysV red zone.


===============================================================================
147. WINDOWS vs SYSV CRITICAL DIFFERENCES
===============================================================================

Windows:

    RCX RDX R8 R9
    32-byte shadow space
    no SysV red zone


Linux/macOS:

    RDI RSI RDX RCX R8 R9
    no Windows-style shadow space
    SysV red zone in applicable user-space code


This difference alone can break assembly interop if ignored.

===============================================================================
151. CRITICAL ABI RULE
===============================================================================

Do NOT think:

    char -> "special char register"
    int  -> "special int register"


Instead:

    ABI first selects argument location/classification.

Then:

    operand width / type representation determines
    how much of that location is relevant.


Example Windows:

    1st integer argument -> RCX family


If int:

    use ECX view


If 64-bit integer:

    use RCX view


If 8-bit:

    use CL view


===============================================================================
152. REGISTER NAMES ARE NOT C VARIABLES
===============================================================================

C:

    int a;


Assembly:

    ECX


does NOT mean:

    "ECX is variable a"


It means:

    "the value corresponding to a is currently in ECX
     under this ABI/calling context."


Compiler may move it:

    mov eax, ecx


Now:

    EAX contains the value.


Variable name "a" may disappear completely from optimized machine code.


===============================================================================
153. OPTIMIZATION
===============================================================================

C:

    int add(int a, int b)
    {
        return a + b;
    }


Compiler may generate:

    lea eax, [rdi + rsi]


instead of:

    mov eax, edi
    add eax, esi


Both can represent the same computation.


Therefore:

    C source structure
        !=
    exact assembly structure


===============================================================================
154. INLINE FUNCTIONS
===============================================================================

Compiler may completely eliminate:

    call


and inline function body.


Then no actual function-call register transfer may exist at runtime.


This is why reverse engineering must reason about generated machine code,
not only source code.


===============================================================================
155. TAIL CALL
===============================================================================

A function may replace:

    call target
    ret


with something like:

    jmp target


when ABI/stack conditions allow it.


This is:

    tail call


Call stack behavior becomes different.


===============================================================================
156. RECURSION
===============================================================================

Function calls itself:

    call function


Each invocation normally needs its own:

    return state
    locals
    saved state


Stack is therefore important for recursion.


===============================================================================
157. STACK OVERFLOW
===============================================================================

Too much stack usage:

    recursion
    huge local arrays
    deep call chains


can exhaust stack memory.


Stack size is OS/runtime dependent.


===============================================================================
158. HEAP
===============================================================================

Heap is dynamically allocated memory.


C:

    malloc
    free


C++:

    new
    delete


Modern C++ often uses:

    RAII
    smart pointers


Assembly can call allocator APIs if ABI is followed.


===============================================================================
159. MEMORY ALLOCATION IS NOT AN ASSEMBLY FEATURE
===============================================================================

NASM itself does not provide:

    malloc


NASM creates machine-code/data object files.


Allocation comes from:

    OS
    runtime
    libc
    Windows APIs
    custom allocator


===============================================================================
160. FILE I/O
===============================================================================

Assembly itself does not magically provide:

    fopen
    CreateFile
    read
    write


These are APIs/system interfaces.


Assembly can call them.


For portability:

    C/C++ standard library
    OS APIs

are usually easier.


===============================================================================
161. WINDOWS vs LINUX vs macOS APIs

    Win32
    Windows SDK
    NT interfaces

    POSIX
    libc

    POSIX

===============================================================================
162. ASSEMBLY PORTABILITY
===============================================================================

This:

    mov eax, edi


is not portable between:

    Windows x64
    SysV x86-64


because argument register differs.


Portable assembly requires:

    architecture
    OS
    ABI
    object format
    linker
    symbol conventions

to all match.

163. NASM vs MASM
===============================================================================

NASM:

    Intel-style syntax
    cross-platform
    independent assembler


MASM:

    Microsoft Macro Assembler
    Microsoft ecosystem


Both are Intel syntax families but syntax/directives differ.


Do not mix NASM directives with MASM syntax blindly.


===============================================================================
164. NASM vs GAS
===============================================================================

    Intel-style

    AT&T syntax

Example conceptual difference:

NASM:

    mov eax, ebx


AT&T:

    movl %ebx, %eax


NASM:

    destination, source


AT&T:

    source, destination

182. 32-BIT vs 64-BIT
===============================================================================

    ECX
    EDX

===============================================================================
183. 16-BIT / 8-BIT ARE NOT "CPU MODES"
===============================================================================

    AX
    AL

===============================================================================
184. MEMORY SIZE vs REGISTER SIZE
===============================================================================

Example:

    mov eax, [rbx]


Register:

    EAX = 32-bit


Memory operand:

    32-bit because destination determines size.


For ambiguous memory:

    mov dword [rbx], 10


Explicitly tells assembler:

    write 32 bits.

    WORD  = 16
    DWORD = 32

    1 BYTE  = 8 bits
    1 WORD  = 2 bytes
    1 DWORD = 4 bytes
    1 QWORD = 8 bytes

===============================================================================
188. ASSEMBLY FUNCTION CONTRACT
===============================================================================

A function can be thought of as:

    INPUT CONTRACT
        |
        +--> argument locations
        +--> argument types/widths
        +--> stack requirements
        |
        v
      FUNCTION
        |
        +--> preserve required registers
        +--> modify allowed registers
        |
        v
    OUTPUT CONTRACT
        |
        +--> return register
        +--> memory side effects


That contract is ABI.

189. FUNCTION EXAMPLE
===============================================================================

    b -> RDX
    result -> RAX

        ret

    a -> RDI
    b -> RSI

    global add64

        mov rax, rdi
        add rax, rsi
        ret

190. FLOAT EXAMPLE
===============================================================================

    XMM0 = a
    XMM1 = b

    result -> XMM0

    addsd xmm0, xmm1
    ret


Windows:

    corresponding first two FP argument positions:

    XMM0
    XMM1

and result:

    XMM0

191. POINTER EXAMPLE
===============================================================================

    long long read(long long *p);

    mov rax, [rdi]

===============================================================================
192. ARRAY LOOP EXAMPLE
===============================================================================

C:

    int sum(int *a, int n);


Windows:

    a -> RCX
    n -> RDX


Linux/macOS:

    a -> RDI
    n -> RSI


Conceptual loop:

    sum = 0
    i = 0

    while i < n:

        sum += a[i]

        i++


Assembly must calculate:

    a + i*4


===============================================================================
193. ABI DOES NOT TELL YOU EVERYTHING
===============================================================================

ABI does not mean:

    "all programs use exactly this assembly."


Compiler may choose:

    different instructions
    different register allocation
    different stack layout
    inlining
    vectorization
    tail calls


ABI defines the externally visible contract,
not every internal instruction.


===============================================================================
194. COMPILER REGISTER ALLOCATION
===============================================================================

Compiler may receive:

    a -> RCX


then:

    mov rax, rcx


and later:

    register no longer represents "a"


The compiler may reuse registers.


Therefore source variable identity is not permanent at machine level.

198. GOLDEN RULES
===============================================================================

RULE 1:

    Registers are not C variables.


RULE 2:

    ABI defines function-call contracts.


RULE 3:

    RCX and ECX are different-width views of one register family.


RULE 4:

    32-bit GPR writes zero-extend to 64-bit.


RULE 5:

    8/16-bit writes do not generally zero upper bits.


RULE 6:

    [RAX] means memory at address RAX.


RULE 7:

    RAX means the register value itself.


RULE 8:

    Windows x64 != SysV AMD64.


RULE 9:

    Windows has 32-byte shadow/home space.


RULE 10:

    SysV has a 128-byte red zone in applicable user-space code.


RULE 11:

    C/C++ types are not NASM types.


RULE 12:

    Struct/aggregate ABI rules are more complicated than
    simple integer register mapping.


RULE 13:

    macOS Intel x86-64 != Apple Silicon ARM64.


RULE 14:

    Assembly source != machine code.


RULE 15:

    Machine code != original C source.


RULE 16:

    Linker resolves symbols and relocations.


RULE 17:

    CALL/RET are part of function-control flow,
    not merely "jump instructions."


RULE 18:

    Performance depends on microarchitecture,
    not only instruction count.


RULE 19:

    Do not mix ABIs.


RULE 20:

    Always know:
        architecture + OS + ABI + assembler + object format.
